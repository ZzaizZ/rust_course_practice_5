# Поиск багов и оптимизация кода Rust

## Поиск ошибок

Результаты работы разбиты по коммитам. С помощью MIRI, Valgrind, gdb были найдены ошибки:

- Утечка памяти (обнаружена через valgrind)
- Выход за границы массива (обнаружена через miri)
- Некорректное усреднение (тесты)
- Некорректная нормализация (тесты)

Для, случаев, которых актуально, написаны регрессионные unit-тесты.

## Оптимизация

После исправления была проведена работа по оптимизации. Результаты работы так же отражены в отдельных коммитах.
Результаты замеров на каждом этапе приведены в директории [`/report`](./report/).

Сравнение бенчмарков начального и конечного состояния:

| bench | до оптимизации | после оптимизации | % прироста |
| --- | :---: | :---: | :---: |
| sum_even | [15.418 µs 15.435 µs 15.450 µs] | [20.247 µs 20.265 µs 20.290 µs] | −31.3% |
| slow_fib | [6.8151 ms 6.8908 ms 6.9852 ms] | [24.194 ns 24.270 ns 24.343 ns] | +99.9996% |
| slow_dedup | [10.583 ms 10.613 ms 10.645 ms] | [16.492 µs 16.694 µs 16.916 µs] | +99.84% |

Негативное изменение объясняется первого бенчмарка объясняется погрешностью. Работ по оптимизации этой части не производилось. Отклонения незначительные.

### Краткое описание выполненных оптимизаций

#### slow_fib

- Изначально был приведён медленный рекурсивный алгоритм (сложность O(2^n)).
- На первой итерации он был заменён на алгоритм с мемоизацией, использующей HashMap. Получилась сложность O(n) по времени и O(n) по памяти.
- И на последней итерации алгоритм был заменён на линейный (O(n) по времени, O(1) по памяти). Согласно замерам это самый быстрый алгоритм.

#### slow_dedup

- Изначальный алгоритм имел сложность O(n^2) по времени.
- На первом этапе оптимизации алгоритм был переписан на использование BTreeSet. Получилась сложность O(n log n) по
  времени. Бенчмарки показали значительный прирост.
- На последней итерации была произведена микро-оптимизация с использовнием вектора + сортировки. За счёт кэш-локальности
  согласно бенчмаркам так же получилось добиться прироста.
